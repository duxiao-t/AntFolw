# AntFlow 生产环境全量压测报告

测试时间：2026-08-24 19:17–19:37（Asia/Shanghai）

## 结论

本机生产实例的鉴权读接口吞吐上限约为 **7,300–7,850 RPS**。超过 25 个闭环并发后，吞吐基本不再增长，新增并发主要转化为排队延迟。

- **严格满足原接口 p95 目标：100 并发。** 该档所有测试接口均满足 bootstrap < 50ms、列表 < 100ms、详情 < 200ms。
- **推荐持续运行容量：400 并发。** 120 秒持续测试完成 877,371 次请求，零错误，整体 p95 81.69ms；列表 p95 60.72–63.98ms，详情 p95 95.25–99.16ms。
- **可交互高负载上限：约 1,600 并发。** 零错误，整体 p95 285.27ms，所有接口 p95 低于 500ms。
- **约 2,400 并发开始越过 500ms 交互边界。** bootstrap/workplace p95 分别为 504.32ms/504.02ms。
- **最高测试到 4,000 并发，仍无 HTTP 错误，但不建议承载。** 整体 p95 605.28ms、p99 932.19ms，吞吐仍只有 7,494 RPS。

因此，“能接住”的测试上限是 4,000 并发；“用户体验可接受”的上限约 1,600 并发；“建议长期安全运行”的容量为 400 并发；如必须逐项满足原定最严格 p95 指标，则按 100 并发规划。

## 下一瓶颈与建议

1. 当前吞吐在约 7.5k RPS 平台化，但 Java 与 PostgreSQL合计只使用约 12.5 个 CPU 核。下一轮若要提高吞吐，应首先对比 Hikari 10/20 连接，而不是直接扩 JVM 内存。
2. 每请求约 5.11 次数据库提交偏高。应检查会话校验、授权版本校验和业务查询是否被拆成多个自动提交事务；合并只读事务可能比单纯扩大连接池更有效。
3. 如果按原 p95 指标验收，单实例容量按 100 并发规划；如以 500ms 交互边界规划，可按 1,600 并发，但建议至少保留 30% 余量，生产配置按约 1,000 并发/实例更稳妥。
4. 静态文件改由 Nginx/CDN承载；桌面端继续减少首屏执行和渲染延迟，重点检查布局初始化及非关键全局组件。
5. 本次为读流量容量测试。审批写入、流程启动、文件上传、视频后台水印应单独做事务冲突、磁盘和 FFmpeg 并发测试，不能套用本报告的 7.5k RPS。
