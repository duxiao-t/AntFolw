# AntFlow 移动端填报链路 UI/UX 设计规格

日期：2026-07-29

范围：移动端第一阶段 UI/UX 重做，优先覆盖填报链路。
后续阶段：完成本规格后，再单独设计整个移动端壳层的视觉一致性。

## 1. 目标

本阶段解决移动端填报时的视觉疲劳和操作负担。用户在手机上填写请假、报销、采购等动态表单时，应能清楚知道当前填到哪里、还剩多少、哪些字段必须处理，以及提交后会进入什么流程。

第一阶段覆盖：

- 表单填写：`/forms/:code`
- 自选审批人：`/forms/:code/self-select`
- 提交确认：`/forms/:code/confirm`
- 提交成功：`/forms/:code/success/:instanceId`
- 流程进度：`/processes/:instanceId`

第一阶段不覆盖：

- 工作台、应用目录、待办中心、审批详情、我的、草稿箱、账号安全的整体重做
- 后端流程树模型改造
- 新增智能条件表单引擎
- 企业微信免登、JS-SDK、应用消息

这些内容进入第二阶段“移动端视觉一致性”规格。

## 2. 已确认设计决策

### 2.1 主流程

采用“分步引导”。长表单不再一屏到底，而是把一次填写拆成多个短任务。每一步只处理一个主题，顶部显示当前步骤、总步骤和进度。

### 2.2 分步规则

采用“按表单分组推进”。移动端不发明新的业务分组，而是优先使用表单 schema 中已经存在的结构：

1. `span_layout` 作为天然分组。
2. 相邻的 `description` 节点可以作为后续字段组的说明。
3. `table_list` 独立成组。
4. 没有明确分组时，按 4 到 6 个可见字段自动切分为一组。
5. 不可见字段不参与当前步骤计算。

分组推进只影响展示顺序和每屏字段数量，不改变提交数据结构。

### 2.3 视觉语气

采用“蓝绿双轴系统”：

- 蓝色负责品牌、当前步骤、主按钮、流程推进。
- 绿色负责保存、完成、轻提示、低压力反馈。
- 页面背景使用低饱和冷灰，减少长时间填表的眼睛负担。
- 不使用大面积高饱和蓝底，不使用装饰性渐变和浮动图形。

### 2.4 字段体验

填报页默认采用“舒适分组式字段”：

- 标签在控件上方，避免左右扫读。
- 控件触控高度不低于 44px。
- 高频选择字段按钮化，例如单选、多选、常用枚举。
- 长文本、附件、表格子项使用独立区域承载。
- 错误提示就地显示，并自动滚动到当前步骤第一个错误。

确认页采用“紧凑核对式”，用于快速检查字段摘要、审批人和流程路径。

## 3. 体验结构

### 3.1 表单填写页

页面结构：

```text
顶部导航：返回 / 表单名称 / 草稿箱
步骤区：当前步骤名称、步骤序号、进度条、预计字段数量
字段区：当前分组字段
状态区：自动保存或草稿状态
底部操作：保存草稿 / 继续填写 或 下一步
```

行为规则：

- 初次进入显示第一个可见分组。
- 每一步提交前只校验当前分组字段。
- 点击“继续填写”时，如果当前分组有错误，停留在当前步骤并显示错误。
- 最后一步通过后，执行全表校验；若其他步骤存在错误，跳到第一个错误步骤。
- 表单值仍使用现有 `node.id` 作为 key。
- 草稿保存、本地恢复、离开确认沿用现有逻辑。

### 3.2 自选审批人页

页面保持单任务心智：只让用户完成审批人选择。

结构：

```text
顶部导航：返回 / 选择审批人 / 确定
提示卡：说明哪些节点需要用户自选
节点卡：节点名称、选择规则、候选人列表
底部操作：确认审批人
```

行为规则：

- 每个 SELF_SELECT 节点独立成卡。
- 候选人支持搜索和最近选择区。
- 单选与多选视觉必须区分。
- 未完成必选审批人时，就地提示并停留在该节点。

### 3.3 提交确认页

确认页用于“扫一遍再提交”，不再以填报字段样式展示。

结构：

```text
顶部摘要：应用图标、表单名称、状态
申请摘要：紧凑 key/value 列表，支持返回修改
审批流程：流程节点时间线或预览路径
审批人：用户自选结果
底部操作：返回修改 / 确认提交
```

行为规则：

- 字段摘要使用现有 `getFieldDefinition(type).summarize` 能力。
- `description` 节点不进入摘要。
- `table_list` 显示行数摘要，并在后续增强中支持展开。
- 提交失败时保留在确认页，显示明确错误原因。

### 3.4 提交成功页

提交成功页只做结果确认和下一步导航，不堆叠功能。

结构：

```text
成功图形
提交成功
下一步说明
返回工作台 / 查看进度
```

行为规则：

- 直接提交表单显示“提交成功”。
- 审批流程表单显示“申请已进入审批流程，请等待审批人处理”。
- “查看进度”进入 `/processes/:instanceId`。

### 3.5 流程进度页

流程进度页用来回答“现在到哪了、谁在处理、我能做什么”。

结构：

```text
顶部导航：返回 / 流程进度
摘要卡：表单名称、状态、发起时间
进度时间线：已完成、当前、待处理
申请摘要：紧凑 key/value
底部操作：撤回流程
```

行为规则：

- 当前节点使用蓝色强调。
- 已完成节点使用绿色。
- 驳回、撤回、失败使用明确状态色和文案。
- 只有当前用户可撤回且实例可撤回时显示撤回操作。

## 4. 设计系统

### 4.1 色彩

建议 token：

- `--af-color-primary`: `#1769e0`，品牌蓝，主操作和当前步骤。
- `--af-color-success`: `#0f8a5f`，完成、保存、成功反馈。
- `--af-color-bg`: `#f5f8fc`，页面背景，降低眩光。
- `--af-color-surface`: `#ffffff`，字段卡和内容面。
- `--af-color-text`: `#102033`，正文。
- `--af-color-muted`: `#65758a`，辅助说明。
- `--af-color-border`: `#dfe8f4`，边框和分割线。
- `--af-color-danger`: `#b42318`，错误和危险操作。

### 4.2 字体与密度

- 标题：15 到 18px，700 到 820 weight。
- 字段标签：12 到 13px，颜色使用 muted。
- 输入内容：14 到 16px。
- 辅助说明：11 到 12px。
- 控件高度：不低于 44px。
- 字段垂直间距：10 到 14px。

不使用 viewport width 缩放字体。移动端应优先通过分组和留白降低复杂度，而不是把字变小。

### 4.3 形状与层级

- 页面不使用嵌套卡片。
- 分组容器使用 8 到 14px 圆角。
- 底部操作条固定在安全区上方。
- 主要页面保持单列，不使用复杂分栏。
- 卡片阴影克制，优先用背景和边框建立层级。

## 5. 技术落点

### 5.1 分组推进层

新增一个纯函数模块，例如 `mobile/src/features/forms/schema/stepGroups.ts`：

- 输入：schema、values。
- 输出：步骤数组，每个步骤包含 id、title、description、nodes、fieldIds、errorCount。
- 依赖现有 `isVisibleNode`，保证条件隐藏字段不参与分组。
- 不写入 store，不改变 schema。

建议接口：

```ts
type FormStepGroup = {
  id: string;
  title: string;
  description?: string;
  nodes: MobileSchemaNode[];
  fieldIds: string[];
};

function buildFormStepGroups(schema: MobileSchemaNode[], values: MobileFormValues): FormStepGroup[];
```

### 5.2 填报页组件边界

建议拆出：

- `FormStepHeader`：当前步骤、进度条、完成状态。
- `FormStepNavigator`：步骤切换和错误定位。
- `FormStepFields`：当前步骤字段渲染，内部复用 `DynamicFormRenderer`。
- `ConfirmSummaryList`：确认页和流程详情复用的紧凑摘要。

`FormFillPage` 继续负责数据请求、草稿、校验和路由跳转。

### 5.3 字段组件改造

字段组件保持现有 registry 结构。第一阶段只调整视觉和交互：

- `TextField`、`TextareaField`、`NumberField`、`MoneyField` 使用统一舒适字段壳。
- `SelectField`、`RadioField`、`MultiSelectField`、`CheckboxField` 优先用按钮式选择。
- `DateField`、`DateRangeField`、`TimeField` 保持原生可用性，但视觉统一。
- `FileUploadField`、`ImageUploadField` 使用独立上传区，显示上传中、失败、可删除。
- `TableListField` 每行用可展开块，不使用密集表格。

### 5.4 不变的数据流

保持以下现有能力：

- `fetchMobileForm(code)` 获取表单详情。
- `validateSchemaValues` 做最终全表校验。
- `collectVisibleValues` 只提交可见字段。
- `beginSubmitFlow` 缓存提交过程。
- `findSelfSelectRules` 决定是否进入自选审批人。
- 草稿保存和本地恢复逻辑不改变。

## 6. 错误与恢复

- 当前步骤字段错误：就地显示错误，阻止继续。
- 非当前步骤存在错误：步骤入口显示红色错误数量。
- 附件仍在上传：阻止继续，提示“仍有文件未完成上传”。
- 网络失败：保留当前表单值，允许保存草稿或稍后重试。
- 离开页面：继续使用现有离开确认和本地恢复。

错误文案必须告诉用户如何修复，不使用泛化的“操作失败”作为唯一提示。

## 7. 测试策略

### 7.1 单元测试

- `buildFormStepGroups`：
  - 使用 `span_layout` 分组。
  - `description` 作为分组说明。
  - `table_list` 独立成组。
  - 无分组 schema 自动切分。
  - 隐藏字段不计入步骤。
- 字段组件：
  - 必填错误就地显示。
  - 选择类字段按钮可点击并回写。
  - 附件上传状态不丢失。

### 7.2 页面测试

- 表单填写：
  - 第一步只渲染当前分组。
  - 当前步骤错误时不能进入下一步。
  - 最后一步全表校验后进入自选审批人或确认页。
  - 草稿保存和恢复仍可用。
- 提交确认：
  - 摘要显示字段值。
  - 返回修改能回到填写页。
  - 提交成功后进入成功页。

### 7.3 视觉与门禁

- 更新填报链路关键页视觉基线。
- 运行 `npm run lint`、`npm test`、`npm run build`、`npm run check:bundle`。
- 第一阶段不要求后端测试，除非实现中发现 API 契约问题。

## 8. 验收标准

第一阶段完成时应满足：

1. 表单填写页按分组分步展示，不再长表单一屏到底。
2. 蓝绿双轴视觉在填报链路内一致。
3. 高频选择字段比普通 input 更容易点选。
4. 当前步骤错误可定位，跨步骤错误可回跳。
5. 草稿、恢复、附件、自选审批人、确认提交、成功页、流程进度不退化。
6. 移动端单测、构建、bundle budget 通过。
7. 移动端 lint 阻断项清理完成。

## 9. 第二阶段边界

第二阶段单独处理移动端视觉一致性，范围包括：

- 登录
- 工作台
- 全部应用
- 常用应用管理
- 待办中心
- 审批详情
- 我的
- 草稿箱
- 账号与安全
- 离线、空状态、错误状态

第二阶段应复用第一阶段确立的蓝绿双轴 token、字段密度、底部操作条和状态表达，不重新发明另一套视觉语言。
